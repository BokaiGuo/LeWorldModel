# P1 反馈节点：旧计划尾部与新候选同评分

已知根 0 的干预只说明 cp5 赢家连续执行两包在该条前缀于
总步 15 成功；原在线 cp10 重规划轨迹总步 20 未成功。它不证明
保留策略会被当前模型选中，也不证明反馈代码错误。

## 方法和接入

独立组件 `p1_rgb_carry_replan_codex_20261101.select` 不启动模型、
环境或 GPU。调用方须：

1. 在 cp5 保存模型实际选中且 refinement 接受后的完整原始动作计划；
   不从物理结果或事后赢家重建计划。
2. 执行选中计划的第一包，采集该分支的当前 RGB，按既有编码器与
   执行动作历史构造当前 `states`、`history`、`goal` 及动作归一化参数。
3. 按既有方式生成新候选；将其和 cp5 计划的未执行尾部传入组件。
   此例尾部两包，新候选统一截取前两包，所有候选从同一当前上下文
   逐一使用冻结模型终点 latent MSE 重新评分；相同分数保留旧计划。
4. 实际执行结果的 `selected_raw[0]`；下一次反馈保存本次完整
   `selected_raw` 作为上一计划。尾部耗尽时不得传入过期计划：
   用 `previous_selected=None` 开启新计划。执行器必须另行实现
   时间、分支、RGB、实际已发命令及计划身份绑定并封存决策。

接口不接收物理状态、成功标签、事后选择动作或旧评分，但不能
仅凭张量检查证明调用者的数据来源。须在集成层验证来源与时序。
模型误差、评分视野由 H3 改为 H2，以及旧计划可能不被选中，都
可能导致该方法仍失败。

## 费用和验证边界

新评分的增量为 `(N+1)*H` 次 action encoder、predict 和
predict sample，`N+1` 次 replay 与 selection，无反向传播；
其中 N 是新候选数，H 是旧计划剩余包数。N=8、H=2 时分别为
18、18、18、9、9、0。计数由叶子接口逐次收取；调用前必须
在独立合同中增加并预留相应上限，不能直接套用原预算。
这不包含 RGB 编码、新候选生成和优化、物理执行、耗时或显存；
也不等同 FLOPs 或公平预算。旧的 H3 候选筛选/优化成本仍须另计。

CPU 单元测试采用虚构叶子模型，只验证选择逻辑与计数，不验证
真实模型、GPU 调用、在线时序或物理效果。下一步需要新建独占
执行器和预算合同、绑定实际 RGB/模型与计划来源，先做 CPU 接口
验证，再在资源允许且授权后做真实节点与物理对照；不可把本次
测试当成真实结果。
