# E0 goal-relative waypoint search: prospective development diagnostic

## Question and limits

Does allocating part of a fixed search budget to goal-relative intermediate
targets improve complete-chain coverage compared with the existing v11
recursive response compiler and a three-start direct CEM? The motivation is
the sealed v10 result: complete chains rarely got around the wall and neither
fixed automatic prefixes nor finite suffix searches succeeded. This does not
identify a bug. The proposed 2-D waypoint geometry and offset scale are a
hand-designed inductive bias informed by the exposed wall family, not
dynamics-discovered modes, a spectral contribution, or the v11 method.
The diagnostic is not a PC2 or PC3 confirmation.

## Fixed tasks and arms

Use the Cartesian product of start `[-0.5, y, theta]`, `y` in
`{-0.18, 0.19}`, `theta` in `{-0.65, 0.45}`, and goal `[0.5, gy]`,
`gy` in `{-0.07, 0.13}`, in that order: eight development roots. They must
not equal any task in the previously cited v5 or v10 panels; broader historical
independence is unknown. No change, sample addition or root selection based on
outcomes. Fixed success is terminal distance `<0.05` after 15 actions.

Each arm has 1920 prediction tokens with five physical steps per token;
candidate generation, initial scores, suffix search, full-chain refinement
and paired comparison all count. Actions are float32 and bounded [-1,1].

1. **waypoint-CEM**, a new non-spectral development baseline: evaluate the
   five-step zero prefix to obtain feature `x0`. Form two waypoint vectors
   `x0 + 0.5*(goal-x0) ± 1.2*R90(goal-x0)`. For each, optimize a five-step
   prefix from zero using the existing CEM, four knots, 160 scored samples and
   a separate fixed seed; score by distance to its own waypoint. For each
   resulting prefix, evaluate the zero suffix and optimize a 10-step suffix
   with 220 samples, four knots, goal distance and a separate fixed seed.
   Retain the best *full* chain among every evaluation, including initial zero.
   Use remaining complete-chain capacity, less the final paired reservation,
   to refine that best chain jointly with the same four-knot CEM. Finally
   rescore incumbent and its zero-first-five counterfactual together and
   choose the lower score, ties favoring the counterfactual.
2. **v11 response**: same `Config` and nominal actions as the existing v10
   one-mode development arm, but execute v11 with explicit packet length 5,
   no carry and the same 1920-token cap.
3. **direct three-start CEM**: use the exact allocation, initialization and
   algorithm of `cem_smooth` in the sealed v10 runner, on these new roots.

All seeds are deterministic functions of root index, declared in the runner.
Any proposed waypoint solution is generated by optimization, not by a
privileged witness, but the waypoint geometry itself is hand-designed. The
mechanism needed for PC2 is not implied even by a successful chain.

## Records, audit and stopping

Before planning, freeze task grid, protocol and code dependency hashes.
Save every actual action/feature/score batch and selected complete chain.
Recompute all endpoint scores, accounting, selected-incumbent and waypoint
prefix records using the same backend. Report per-root failures, complete
distances, counts, computation time, and each waypoint prefix's intermediate
and final quality. A same-backend audit is not an independent environment.
Stop after all eight roots once; no retries, tuning on this panel, post-hoc
threshold changes, or claims of independent confirmation. If an arm fails,
record the failure and preserve the denominator.
