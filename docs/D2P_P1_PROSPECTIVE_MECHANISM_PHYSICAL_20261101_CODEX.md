# P1 prospective mechanism: physical replay seam, not confirmation

This is new executable physical infrastructure for the *proposed*, not-yet-frozen S/G/Z design in `D2P_P1_COHERENT_CONFIRMATION_DESIGN_20261101_HYPATIA.md`. It does not choose roots, make plans, evaluate models or establish a prospective cohort. Existing known-root common-tail and own-suffix programs are retained and not rerun. No gate is changed.

One invocation consumes one externally SHA-bound presealed input JSON and runs all nine logical branches in fixed order S/G/Z × common/zero/own, without deduplicating identical actions. Common is exactly S's supplied own suffix, zero is 15 zero actions, and own is that role's supplied suffix. Before each suffix, actual cp5 state7, exported two-body dynamics and RGB digests must match that role's supplied planning receipt; root state/dynamics, goal, actual actions and all three warmup RGBs are also checked. Rendering is checked against changing exported dynamics. Each branch recreates the environment, replays ten warmup actions, and uses the existing native evaluator. Actual executed actions, attempted and returned reset/warmup/render/physical steps, checkpoints, native stop/censor and errors are retained. A failure is retained and stops subsequent branches, which remain explicit `not_started`. The cooperative GPU lock covers the physical callback (rendering may use GPU); there are zero neural calls here.

Input schema is `p1_prospective_mechanism_physical_20261101_codex.input.v1`: `sources` is a nonempty mapping of absolute file paths to SHA-256; `source_evidence` and `planning_evidence` are nonempty lists of paths in that mapping. `root` contains integer `reset_seed`, seven-element `requested_reset`, `placeholder_goal`, `goal_state`, `root_state`, `root_dynamics_sha256`, ten-by-two `warmup_raw`, and `warmup_rgb`, a list of three `{path,pixel_sha256}` objects for 224×224 RGB PNGs in `sources`. `roles` has exactly keys `S`, `G`, `Z`, each with `prefix_raw` (5×2), `own_suffix_raw` (15×2), `cp5_pixel_sha256`, `cp5_state_identity_sha256`, `cp5_dynamics_sha256`; state and dynamics use the project's canonical JSON digest of state7 and `native_source.snapshot(body)` respectively. Raw actions must be finite and bounded in [-1,1], and Z prefix must be zero. Source bytes and all images are checked before physical work; input file SHA is supplied externally. `protocol.json` is written before branch execution and includes all 20-step commands and source hashes.

**Critical boundaries:** hashes bind bytes, not trust, timing or scientific validity. This seam does not verify a source authority, registry completeness, family independence, same-bank greedy scoring, model-selected S, own-suffix argmin, node/encoding budgets, Q, planning trace, or absence of future-outcome leakage. Exported two-body dynamics explicitly omit solver warm-start cache and do not establish full dynamical identity. `source_and_plan_provenance=unverified`, `independent_confirmation=false` and `P1_admission=false` are hard-coded. Replaying supplied actions does not repair those gaps. A valid confirmation requires separate source qualification and sealed upstream producer/consumer verification, prespecified metrics, margins, sample and inference, real-RGB causal context and complete accounting, a fair strong baseline, and adjudication against all existing gates. Do not use this entry point for a confirmation run until those contracts are fixed.
