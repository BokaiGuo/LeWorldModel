# Successor-program RGB execution development protocol

Purpose: connect dynamics-generated successor composition, complete-chain
selection, joint refinement, final-chain abstention and fixed-terminal RGB
feedback in one development execution path. This is not a frozen PC method
or an independent confirmation. The four existing roots are exposed; no
outcome from them may be treated as independent evidence.

At the 15-step decision generate a zero and a response proposal around one
fixed nominal first segment. At each resulting successor, generate a zero
and response proposal using the same nominal and response routine. Form all
four ten-step prefixes. Assign each the same multi-batch CEM suffix policy;
reserve one quarter of the remaining affordable full-chain samples for joint
refinement. Select by complete terminal score and compare against the
rescored carry where available. At 10 and 5 remaining steps use the existing
multi-nominal fixed-terminal policy. Finally compare the actual selected
chain against its zero-prefix, unchanged-suffix counterfactual. Ties use the
counterfactual. Record the pre-comparison chain and all model calls.

Compare with direct CEM under the same 480 prediction-token cap at each
decision and with the same three feedback observations and reserved final
prediction. The cap accounts for predicted action packets, including response
extraction, candidate search, refinement, carry and final comparison.
Encoding, SVD, GPU time and physical interaction are reported separately;
this is not certified equality of total cost. No oracle plans or physical
outcomes enter selection.

Report each root and arm, final distance, action and prediction traces, all
costs, and abstention. Replay actual actions in the native physical backend.
Do not modify historical outcomes or claim PC2 from this performance run.
Do not alter the stopped wall or PointMaze non-immediate protocols.
