# v25 搜索宽度与资源曲线：开发结果

按 [事前协议](PC_V25_BEAM_RESOURCE_CURVE_DEV_PROTOCOL_20261104_CODEX.md)，16 根新开发任务、三臂、两个 token 上限的 96 次规划全部完成并通过审计。共享 CEM 与两种 v25 配置使用相同全局候选库；窄束配置从宽束的 beam 4／greedy 2 改为 beam 2／greedy 1。

| token 上限 | 方法 | 成功根 | 平均终距 | 精修完整链样本／根 |
| ---: | --- | ---: | ---: | ---: |
| 1,920 | 宽束 v25 | 0/16 | 0.4486 | 109–120 |
| 1,920 | 窄束 v25 | 0/16 | 0.4019 | 294–304 |
| 1,920 | 共享 CEM | 2/16 | 0.3245 | 573 |
| 2,880 | 宽束 v25 | 1/16 | 0.3724 | 422–438 |
| 2,880 | 窄束 v25 | 2/16 | 0.3627 | 614–624 |
| 2,880 | 共享 CEM | 3/16 | 0.2945 | 893 |

以 `1e-12` 为相等容差，窄束相对宽束的逐根终距：1,920 时 13 优、1 平、2 劣；2,880 时 11 优、4 平、1 劣。窄束相对共享 CEM：1,920 时 3 优、1 平、12 劣；2,880 时 4 优、4 平、8 劣。宽束执行 18 次 SVD，窄束执行 10 次；后继探针分别为 6–8 和 8 次。部分响应臂因 packet 整数余数少用 1–2 token，其余用满上限。

结论：本面板支持继续研究搜索宽度与精修预算的联合分配；窄束在多数根降低终距，但 1,920 上没有成功率改善，且两预算点的共享 CEM 成功数和平均终距均更好。束宽改变了保留及后继候选，不能把差异单独归因于精修预算或响应有效性。预算点并非嵌套，结果不是证明更多预算必然改善同一条搜索轨迹。

事后按独立的[可行性诊断协议](PC_V25_BEAM_RESOURCE_FEASIBILITY_POSTHOC_PROTOCOL_20261104_CODEX.md)，16/16 根有至少一条符合 15 步动作域和成功阈值的特权几何见证，动作与另一同环境实现核对；原始见证见 `feasibility_posthoc.json`。这不证明在声明预算内找到见证，也不是正式方法的成绩。

所有逐批动作、预测账本及依赖保存在 `le-wm-main/results/pc_v25_beam_resource_curve_dev_20261104_codex/`；审计核验请求计费、同环境另一几何实现、选中链为已评分完整链最优、共同候选库及整个规划器逐批确定性重放。重放不是独立复现；外部训练来源和完整 GPU／编码成本未知，也未做同链机制干预。这不是 PC0–PC5 通过证据或理论否定。

复现命令（在 `le-wm-main`）：`.venv/bin/python -m experiments.pc_v25_beam_resource_curve_dev_20261104_codex run`，再运行相同命令并将 `run` 改为 `audit`。程序拒绝覆盖既有结果。
