# P1 H4 preparation (not a physical runner)

The independent `p1_h4_parfit_20261101.py` contains candidate, gradient-mask,
exchange, feedback-selection and prospective operation-count primitives. It
does not call `setup` or patch the active H3 control chain. It is not a
complete wrapper and cannot launch a model or an environment.

Proposed schedule is H4/H3/H2/H1 at boundaries 0/5/10/15, respectively.
The first boundary protects each original first packet during all six
normalized updates. Every subsequent boundary compares eight freshly
optimized candidates against the *actual prior selected plan's* remaining
tail, all at the same horizon, with ties favoring the tail. H2 through H4
exchange all eight prefixes with all eight tails (64 full-horizon scores);
H1 has no tail exchange. The full Q objective, independent per-candidate
six updates, and immediate-progress screening match the existing design.

For each node, counts include eight times six optimization rollouts and
eight final rollouts, one H-step Jacobian rollout plus 192 VJPs and one SVD
for structured, sixteen one-step screen rollouts for immediate-progress,
64 H-step exchange rollouts if H>1, and nine H-step feedback rollouts at
boundaries 5/10/15. Their expected counters are in `node_cost`; a CPU test
independently enumerates that event schedule. It is not live metering:
visual encoding, physical steps, environment cost and metric construction
are excluded. Arms retain different initializer costs; equal candidate
allocation is not equal total compute.

## Required integration work

1. Make a genuinely independent physical launcher, rather than patching the
   currently running module globals. Preserve the source/protocol hash seals,
   four-arm task/metric identities, exclusive output and host authority checks.
2. Replace every H3 ABI in the real planner and bridge: candidate allocation,
   H4 raw rollout, 192x40 Jacobian, response bank, optimizer, first-packet
   extraction, event/receipt schema, and replay verification. At H3/H2/H1
   zero Jacobian columns beyond the active horizon; retain full-width fresh
   storage but select/execute only the active plan.
3. Bind the full selected plan to the driver's *returned* raw packet and
   current RGB/latent encoding, and verify actual normalized history before
   invoking feedback selection. Persist selection and immutable plan identity.
   A score callback alone proves neither provenance nor model evaluation.
4. Reserve the node's full vector before dispatch, measure leaf/backend calls
   including failures, reconcile the consumed durable ledger with
   `node_cost`, and independently reconcile hooks and physical/visual costs.
   Check budgets across all arms and all four boundaries; reserve capacity
   for the 64-way exchange and nine-way carry rescore before performing them.
5. Test actual per-node contract/config binding, H4 full-plan receipt and
   action identity, shortened feedback tails, current RGB identity, budget
   exhaustion and failed-call charging, exclusive output, and replay.
   Only after these pass and host authorization is supplied should a new,
   separately named CUDA run be considered.

The CPU tests exercise pure arrays and tensors, not a neural model, simulator,
GPU, current experiment, or real ledger. Whether the current H3/15-step
truncation loses a 20-step program benefit is an untested hypothesis; these
primitives do not establish P1 or any comparative performance result.
