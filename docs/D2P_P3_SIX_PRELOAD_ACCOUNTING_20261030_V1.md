# P3 六槽加载前全链记账设计与离线验证

## 现有边界

现有 `load_compatible_pretrained` 可在一次调用内触发 CUDA、解析配置、构造模型、读取 checkpoint、重映射权重、迁移设备并冻结模型。现有 guarded host 接受已加载模型，其内部 store 墙钟从主机身份快照之后才开始。因此不能把该 store 的限额解释成从进程启动或模型加载开始的全成本；也不能把旧四槽限额替换成六槽准入。

## 新接缝

新增独立的离线可注入记账模块，不导入模型加载器、torch、GPU 或物理模块，也不是生产 launcher。入口先读取单调时钟，再验证外层计划和已固定 host 计划哈希；随后按上下文创建、checkpoint/模型加载、六槽 host 的顺序执行注入回调。每阶段前后及回调主动提供的内部边界都记录墙钟、RSS 峰值、CUDA allocator 分配/保留峰值和逻辑 checkpoint 读取累计值，并按调用方显式上限检查。CUDA 初始化前的 allocator 值允许 unknown；初始化之后缺失必需计数、超限或计数回退会阻断后续阶段。进入 host 前要求剩余总墙钟至少覆盖其固定的 host 墙钟上限，且 host 的 allocator 上限不能超过全链上限；不修改 host 预算。

独占 journal 按记录链写入、每次 fsync，并预留故障记录空间；阶段异常或守卫失败保留 intent 和尽力写 failure，守卫失败不可被回调吞掉后视为成功。输出只关联 host 回调给出的四个哈希，始终标记 `accounting_complete=false`、`physical_certified=false`、`scientific_pass=false`。这些输入和计数均为调用方提供，不能单独证明身份、来源、实际硬件或执行。

## 未闭合的真实运行接线

- 新接缝尚未接入真实加载器或 guarded host；后者当前没有可注入的外层连续 guard，真实适配需要明确改造或新的独占入口，再完成来源和保存消费审核。
- 加载器内部配置/权重读取与设备迁移没有现成的可信逐项计量接口；模拟的逻辑读取计数不证明所有真实读取被覆盖。内核物理 I/O、文件缓存、驱动/外部 GPU 内存、连续峰值和 FLOPs 均为 unknown。
- 时钟从本函数进入开始，不包含 Python 进程启动、导入及先前 CUDA 初始化；最终 journal 尾部写入的耗时也没有完成后再测，均不能算作已证明的全进程成本。采样之间也可能超限。
- 资源采样和模型/host 回调可以自报；host 输出哈希目前未调用 guarded saved consumer，host 计划是否实际执行、真实设备及权重身份均为 unknown。journal 的本地哈希不是可信时间戳或独立证明；日志故障时失败记录也可能缺失。
- journal 上限单独约束记录字节，并非已完成与六槽输出、磁盘空闲及所有临时文件的联合准入；模型加载失败后的所有资源回收也未证明。

上述 unknown 显式出现在返回值和 journal 首尾，不转换为零或通过。不得据离线测试声称生产准入、完整记账、等资源或公平通过。

## 验证

禁用 CUDA 可见性的 CPU 替身测试和相关回归共 50 项通过，覆盖阶段顺序、超限、unknown、计数回退、时钟异常、固定 host 墙钟不足、失败留痕、日志上限和不可覆盖。未加载权重，未探测或初始化 GPU，未运行物理环境。
