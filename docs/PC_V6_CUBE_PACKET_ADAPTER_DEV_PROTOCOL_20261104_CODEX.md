# v6 Cube packet 适配：事前开发协议

目的：检查 v6 的五维原始动作是否能以训练时的时间顺序和归一化进入原冻结 Cube 模型，并与原 P0 的 root-anchored rollout 比较。此工作是接口诊断，不是规划成功、物理响应或 PC gate 确认。

保持 v6 核心不变。动作每步五维，物理范围 `[-1,1]^5`，连续五步按时间优先展平为一个 25 维 packet；采用源收据中训练前 packet 化的均值与标准差。使用三帧因果 RGB 历史，根帧替代历史末帧，预测时使用 `history[1:] + future`。目标图像仅作为明确给定的视觉目标；本阶段若使用同一源 episode 的未来图像，只表示离线目标条件诊断，不能宣称部署时的目标来源或训练外独立性。

先在合成模型上核对打包顺序、归一化、边界拒绝、缓存模型逐 packet 推进和 root-anchored 参考 rollout，覆盖 5、10、15 步。随后仅在数据、checkpoint 和收据哈希匹配、GPU 可用且遵守共享锁时，另行运行冻结模型源上下文对照；保存输入哈希、动作、预测误差与环境信息，任何结果单列。不得把 evaluator 物理状态输入规划器，不能用修复 checkpoint 替代原模型。对于二维目标 chart 的信息损失、本地响应与真实物理的一致性，本协议不作认证。

首次真实对照记录了高于预设容差的差异，并在结果写出之后因输出打印参数错误退出。后续诊断另存 v2，不覆盖首次结果：在同一动作和上下文上，增加缓存路径批量与逐条结果的比较，并检查完整 latent 最大误差，以区分批处理数值差异与缓存路径或参考路径差异；打印参数单独修复。此诊断不调整容差或模型。

v2 显示单条缓存预测与逐条参考基本一致，而批量预测存在差异。v3 单独关闭 CUDA matmul 和 cuDNN 的 TF32，重复同样的动作及比较并记录设置；如差异依旧，不得断言 TF32 是原因。保留 v1/v2 结果，v3 不替代它们。
